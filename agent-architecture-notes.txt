0. КОНТЕКСТ / ЗАЧЕМ ВООБЩЕ ОБСУЖДАЛИ
--------------------------------------------------------------------------------
Проект скоро переносится во внутренний контур банка с подключением ЛОКАЛЬНОЙ
модели Qwen (~30-32B, точного «35B» нет: есть Qwen2.5-32B, Qwen3-32B,
Qwen3-30B-A3B MoE) вместо текущего Anthropic Haiku.

Пошли от конкретной находки инвентаризации (пункт A2):
инструменты (все 15, TOOL_DEFINITIONS) отправляются модели НА КАЖДЫЙ запрос,
независимо от активного агента. Отсюда родился вопрос про скоупинг инструментов,
а из него — большой разговор про то, чем вообще должны быть «агенты».

ВАЖНОЕ ФАКТИЧЕСКОЕ УТОЧНЕНИЕ (всплыло в обсуждении):
- system-промпт УЖЕ скоупится — уходит base + промпт ОДНОГО активного агента
  (AIPanelSider.tsx:1328-1330), а НЕ промпты всех агентов. Это частое
  заблуждение. Целиком/всегда уходят только ИНСТРУМЕНТЫ.
- Текущий цикл (AIPanelSider.tsx:1320) УЖЕ агентный: модель вызывает инструменты
  и итерирует до stop_reason != tool_use. То есть агенты — это не «просто
  промпты», это промпт + общий агентный цикл + общий (полный) набор инструментов.

1. КАКИЕ ВАРИАНТЫ РАССМАТРИВАЛИ
--------------------------------------------------------------------------------
Спектр «насколько агент — полноценный агент», от малого к большому:

Вариант 1 — Пресеты промптов (КАК СЕЙЧАС).
  Агент = system-промпт + общие инструменты + общий цикл. «Роутинг» = юзер
  вручную выбирает промпт.

Вариант 2 — Скоупленные агенты (капсулы).
  Каждый агент = промпт + СВОЙ набор инструментов + свой контракт вывода.
  Одна модель, один цикл. Небольшое изменение поверх текущего.

Вариант 3 — Оркестратор + специалисты (мультиагент), паттерн «агент-как-инструмент».
  Супервайзер, чьи ИНСТРУМЕНТЫ — это сами специалисты (ask_metrics_agent, ...).
  Модель-оркестратор сама решает кого вызвать, может вызвать нескольких по
  цепочке (метрики -> задача) и синтезировать. ВАЖНО: этот вариант ПОГЛОЩАЕТ
  роутинг — отдельный классификатор не нужен, «маршрутизация» = обычный выбор
  инструмента. Изначально я склонялся сюда.

Вариант 4 — Автономные агенты с памятью и хендоффом (OpenAI Swarm-стиль).
  Долгоживущие сущности, передают управление друг другу, фон. Максимум мощности
  и сложности. Для нашей задачи избыточно.

Отдельная под-идея (обсуждали до вариантов) — АВТО-РОУТИНГ через отдельный
лёгкий КЛАССИФИКАТОР: дешёвый вызов модели «верни одну метку агента», потом
основной вызов с этим агентом. Плюс sticky-состояние для многоходовых агентов,
плюс ручной override. Юзер хотел: оставить ручной выбор, но под капотом
авто-роутинг, «главное чтоб работал надёжно».

2. КЛЮЧЕВЫЕ ПРОБЛЕМЫ/ЛОВУШКИ, КОТОРЫЕ ВЫЯВИЛИ
--------------------------------------------------------------------------------
(A) МНОГОХОДОВЫЕ АГЕНТЫ С СОСТОЯНИЕМ (человек-в-цикле). Самая коварная.
    QBR: показывает metric-selector -> ЖДЁТ клик юзера -> генерит HTML-отчёт.
    CJM Режим 0: предлагает варианты -> ЖДЁТ выбор -> Режим 1 создаёт карту.
    - Наивный классификатор, роутящий КАЖДОЕ сообщение, между ходами переключит
      агента (юзер прислал «выбрал метрики id1,id2» — классификатор решит, что
      это агент метрик) и СЛОМАЕТ сценарий. => нужен sticky.
    - Паттерн «агент-как-инструмент» (Вар. 3) плохо ложится на такие агенты:
      sub-agent обычно «запрос->ответ», а тут надо ПОСРЕДИ вернуть UI юзеру.
    - ГЛАВНОЕ: это проблема АРХИТЕКТУРНАЯ, НЕ зависит от размера модели.

(B) ЦЕЛЕВАЯ МОДЕЛЬ — Qwen ~32B, не Claude.
    - Единый мега-промпт (модель сама роутит выбором инструментов): элегантно на
      Claude, но на слабее модели 9 наборов инструкций в одном промпте могут
      дать деградацию форматов вывода.
    - Явный классификатор (узкая задача «1 из N») — проще для слабой модели.
    - НО: Qwen 32B — НЕ слабая модель, function-calling у неё нормальный.
      Я изначально перестраховался с «модель не потянет оркестратор».

(C) «НАДЁЖНО» НЕЛЬЗЯ ГАРАНТИРОВАТЬ БЕЗ ТЕСТА.
    Единственный честный способ — размеченный тест-сет (30-50 фраз юзера ->
    ожидаемый агент/инструмент) как Vitest-тест. Тогда «работает надёжно» = зелёный
    npm test, и регрессии при правке промпта видны сразу. Vitest в проекте уже есть.

Приоритет 2 — НАГРУЗКА (связывающее ограничение!).
  Если дойдёт до релиза — десятки продактов заходят С УТРА одновременно и
  начинают работать с ассистентами. Токены НЕ важны (своё железо), важна
  НАГРУЗКА на инференс, чтоб модель выдержала.
  => нагрузка = ЧИСЛО ПРОХОДОВ МОДЕЛИ (каждый вызов = forward pass = занятый
     GPU-слот) + объём prefill. Оркестратор/классификатор = +1..+N вызовов на

     ЭТОТ ПРИОРИТЕТ НАПРЯМУЮ УБИВАЕТ ОРКЕСТРАТОР. Самое дешёвое по нагрузке —
     ОДИН вызов на реплику, где одна модель сама понимает и сама выбирает
     инструменты (self-routing).

Приоритет 3 — НАДЁЖНОСТЬ ДЛЯ ЛЮБЫХ ПРОДАКТОВ.
  Должен одинаково хорошо работать и для продвинутых, и для тех, кто в ИИ не
  разбирается. Если «тупой» продакт напишет «хочу cjm» или «бриф на исследование»
  и не получит ожидаемого — решит, что сервис тупой, и уйдёт.
  Конкретный кейс: продакт выбрал агента Трендвотчер, забыл про это, потом просит
  поставить задачу — должно всё равно сработать.

4. РАЗВОРОТ ПРО PREFIX CACHING (важно — отменяет прежний совет по A2)
--------------------------------------------------------------------------------
Раньше советовал ДИНАМИЧЕСКИ резать инструменты под агента (экономия ТОКЕНОВ).
Под НАГРУЗКУ на локальной Qwen калькуляция ПЕРЕВОРАЧИВАЕТСЯ:

- vLLM/SGLang (стандартный стек под Qwen) умеют AUTOMATIC PREFIX CACHING:
  одинаковый префикс (system + инструменты) считается ОДИН раз и переиспользуется
  всеми запросами и всеми юзерами; KV-кэш общего префикса хранится один на всех,
  не по копии на юзера.
- => СТАБИЛЬНЫЙ, одинаковый для всех промпт+инструменты = почти нулевой prefill
  на общую часть у всех утренних юзеров.
- => ДИНАМИЧЕСКИЙ скоуп под агента = у каждого свой префикс = cache miss =
  prefill заново = ХУЖЕ под нагрузкой.
ВЫВОД: держим ОДИН стабильный набор инструментов и один стабильный промпт;
дешевизну даёт prefix-кэш, а не скоупинг. (Локальный аналог пункта A1.)

⚠️ Волатильный контент (дата/имя юзера) НЕ в начало промпта — иначе префикс
«плывёт» и кэш промахивается на каждый запрос. Сейчас base-промпт кладёт дату
наверх (agentPrompts.ts:5-11) — бьёт кэш раз в сутки (терпимо), но время/юзера
туда добавлять НЕЛЬЗЯ. При переписывании — волатильное в конец / в user-сообщение.

5. ИТОГОВОЕ РЕШЕНИЕ
--------------------------------------------------------------------------------
ЕДИНЫЙ SELF-ROUTING АССИСТЕНТ. БЕЗ оркестратора. БЕЗ отдельного классификатора.
Практически текущая архитектура, но с 3 правками:

(1) Ручной выбор агента -> МЯГКАЯ ПОДСКАЗКА, а не жёсткий режим.
    Выбор лишь добавляет акцент в контекст, НЕ отключает остальные инструменты.
    Решает кейс «выбрал Трендвотчера, забыл, просит задачу»: инструмент создания
    задачи никуда не делся -> задача ставится. Залипать не в чем, жёстких режимов
    больше нет. (Закрывает приоритет 3 с нулём лишних вызовов.)

(2) Тяжёлые спеки форматов — из system-промпта В РЕЗУЛЬТАТ ИНСТРУМЕНТА.
    QBR HTML+SVG+CSS (agentPrompts.ts:139-155), детали CJM. Пусть тяжёлая
    инструкция приходит как tool-result ровно когда путь выбран (напр.
    start_qbr_report возвращает шаблон). Держит общий префикс маленьким и
    стабильным + меньше нагрузка на генерацию. Это ровно исходная идея юзера про
    CJM: «вписывать в шаблон, а не заставлять модель писать с нуля».

(3) Обрезка/суммаризация истории (пункт A4) — под нагрузкой критичнее.
    Длинный диалог = большой prefill на каждый ход. Старые tool-результаты
    усекать. Влияет на то, сколько юзеров влезет одновременно.

Плюс: надёжность интента — тест-сет на Vitest (размеченные фразы -> ожидаемое
поведение). Нужен при ЛЮБОЙ архитектуре.

КАК ЛОЖИТСЯ НА ПРИОРИТЕТЫ:
  1 (phase-1): самая близкая к текущей архитектура -> честный тест Qwen vs Haiku.
  2 (нагрузка): 1 вызов/реплику + стабильный prefix-кэш = минимум forward-pass'ов.
  3 (надёжность): нет жёстких режимов -> нечему «залипнуть»; интент на одной
     модели, меряется тестами.

6. ЧТО ЯВНО ОТВЕРГЛИ И ПОЧЕМУ (чтобы не возвращаться по кругу)
--------------------------------------------------------------------------------
- Оркестратор / мультиагент (Вар. 3): красивый, поглощает роутинг, но +N вызовов
  на запрос => проигрывает по приоритету 2 (нагрузка). Ещё и смазал бы phase-1 тест.
- Отдельный классификатор перед каждым сообщением: +1 вызов на реплику => та же
  проблема нагрузки; плюс ломает многоходовые агенты без sticky-логики.
- Динамический скоуп инструментов под агента (прежний A2): бьёт prefix-кэш =>
  хуже под нагрузкой. Заменено на «стабильный набор + prefix caching».
- Жёсткие режимы агентов (как сейчас, где выбор запирает контекст): создают кейс
  «залип в неправильном агенте» => противоречит приоритету 3.

8. ОБНОВЛЕНИЕ (2026-07-23) — позиция разработчика + двухфазный оркестратор
--------------------------------------------------------------------------------
Разработчик, который будет реализовывать, склоняется к ОРКЕСТРАТОРУ (супервизор,
чьи тулы = вызовы других агентов). Его пример: supervisor_prompt со списком
агентов (get_currency / get_weather / generate_joke), супервизор понимает
намерение и вызывает нужный тул, возвращает результат.

ПЕРЕСМОТР БАЛАНСА (честно, в пользу оркестратора — раньше недооценил):
- Чистые изолированные промпты: каждый специалист ВСЕГДА укомплектован своим
  промптом → убирает «перекос», который есть в едином ассистенте (агент метрик
  не знает инструкций агента задач → задача из режима метрик выходит хуже, блок
  task-link может не появиться).
- Фокусный маленький промпт специалиста Qwen 32B выполняет НАДЁЖНЕЕ, чем один
  мега-промпт на 9 ролей. Довод в пользу оркестратора именно под слабую модель.
- Поддерживаемость: добавить агента = добавить тул, не трогая единый промпт.
- Prefix-кэш работает и для набора маленьких стабильных промптов — НЕ аргумент
  против оркестратора (поправка к разделам 4-5 выше).
- Нагрузка: раньше сказал «кратно больше вызовов» — ПРЕУВЕЛИЧЕНИЕ. Реально
  оркестратор ≈ единый + 1 ЛЁГКИЙ проход супервизора на ход (супервизор только
  роутит, тяжёлую работу делает специалист). Под наплывом +1 проход на ход = ~25%
  меньше одновременных юзеров (грубо, если ход в среднем 3 прохода → 4). Реально,
  но не смертельно. Решается замером на phase-1, не спором.

ГЛАВНОЕ ВОЗРАЖЕНИЕ, которое пример разработчика НЕ покрывал:
его агенты (currency/weather/joke) все STATELESS. А у нас QBR и CJM —
человек-в-цикле (показать metric-selector / варианты → ПАУЗА на юзера →
продолжить). «Агент-как-тул» требует синхронного возврата, а тут возврата нет.

РЕШЕНИЕ (предложил юзер, оно СНИМАЕТ это возражение) — ДВУХФАЗНЫЕ stateful-агенты:
  Фаза 1 «Интерактивный сбор» — остаётся у ОРКЕСТРАТОРА. Он грузит метрики,
    показывает metric-selector (QBR) / предлагает варианты (CJM Режим 0), ждёт
    клика юзера, понимает его выбор. Паузу на человека держит супервизор, который
    и так владеет диалогом.
  Фаза 2 «Исполнение» — когда вся инфа собрана, супервизор вызывает специалиста
    как ЧИСТЫЙ stateless-тул: generate_qbr_report(выбранные_метрики) /
    generate_cjm(выбранный_сценарий) → тяжёлая генерация → возврат результата.
  Специалисту достаётся полностью специфицированное ТЗ без пауз — идеально под
  «агент-как-тул» и надёжнее для Qwen. Тяжёлая генерация = 1 проход в конце,
  двойной тяжёлой работы нет → и по нагрузке ок.

ЦЕНА двухфазного варианта (честно): оркестратор ПЕРЕСТАЁТ БЫТЬ ТОНКИМ — он несёт
сценарии сбора (формат metric-selector, логика «предложи варианты», условие
«когда данных достаточно → хендофф») для каждого stateful-флоу. А супервизор —
ГОРЯЧИЙ ПУТЬ (на каждом запросе). Сложность/вес не исчезли, а переехали из
специалиста в супервизор. Размен честный, но горячий путь толще.

ТЕКУЩИЙ ЛИДИРУЮЩИЙ ПОДХОД: оркестратор + двухфазные stateful-агенты (сбор у
супервизора, исполнение у специалиста). Ближе к тому, что будет делать
разработчик. Моё главное возражение (человек-в-цикле) снято.

ДВЕ ИЗМЕРИМЫЕ ВЕЩИ, которые всё равно проверить на phase-1 (не решаются спором):
  (1) насколько потолстевший супервизор бьёт по ёмкости под утренним наплывом;
  (2) надёжность роутинга супервизора — на тест-сете фраз (Vitest). Тест-сет
      нужен при ЛЮБОЙ архитектуре.

9. РЕАЛИЗАЦИЯ (2026-07-27, Сессия 34) — ВЕРТИКАЛЬНЫЙ СРЕЗ ОРКЕСТРАТОРА
--------------------------------------------------------------------------------
Юзер решил реализовать оркестратор + двухфазные специалисты, НО без переписывания
транспорта под Qwen (всё продолжает работать на текущем Anthropic-пути). Сделан
тонкий вертикальный срез для обкатки паттерна (не все 9 агентов сразу).

ЧТО СДЕЛАНО:
- Транспорт не тронут: streamChat -> /api/chat -> Anthropic SDK как есть.
- Оркестратор = главный цикл в AIPanelSider. system = getOrchestratorSystemPrompt()
  (base + каталог специалистов + двухфазный сбор CJM). tools = getOrchestratorTools()
  (все инструменты КРОМЕ create_task_draft + инструменты-специалисты).
- Специалисты (src/lib/specialists.ts), паттерн «агент-как-инструмент»:
  * write_task_draft — EXECUTION-ONLY промпт (не переиспользует интерактивный
    agent-tasks!). Владеет create_task_draft эксклюзивно -> карточка task-link
    гарантирована при любом входе (закрыт баг «голого линка» из общего чата).
  * generate_cjm — переиспользует промпт agent-cjm, только СОЗДАНИЕ (Режим 0 в нём
    не триггерится на конкретном ТЗ). Правка/актуализация/проверка-артефакта CJM
    НЕ делегируются — остаются инлайн у оркестратора (интерактивные, stateful).
  Вызов специалиста -> runSpecialist(): вложенный агентный цикл со стримом в
  отдельный видимый пузырь (карточки рендерятся штатно) + компактный tool_result
  оркестратору (тяжёлый контент не гоняется обратно в супервизор).
- Ручной чип агента -> МЯГКАЯ ПОДСКАЗКА (раздел 5(1) выполнен): не подменяет system,
  а добавляет акцент/guidance; инструменты не отключаются. agent-tasks -> только
  focus-строка (создание у специалиста); остальные 7 (вкл. agent-cjm) -> их промпт
  как guidance, чтобы инлайн-сценарии (правка/отвязка артефакта CJM, QBR) не ломались.

КЛЮЧЕВОЙ УРОК РЕАЛИЗАЦИИ (подтвердил проблему (A) из раздела 2):
  Нельзя оборачивать ИНТЕРАКТИВНЫЙ промпт агента в stateless-специалиста —
  agent-tasks Режим 1 задаёт уточнения и просит «сохранить?», специалист бы задал
  вопрос и ПОТЕРЯЛ состояние (ответ юзера уходит оркестратору, не специалисту).
  => специалист должен быть EXECUTION-ONLY, а весь человек-в-цикле (сбор/уточнения)
  держит оркестратор. Это ровно двухфазная модель из раздела 8, проверенная на коде.

10. УРОКИ СРЕЗА -> ОБЯЗАТЕЛЬНО УЧЕСТЬ ПРИ ПЕРЕВОДЕ ОСТАЛЬНЫХ АГЕНТОВ
--------------------------------------------------------------------------------
Всё, что вскрылось на срезе (Сессия 34). Это чек-лист для перевода каждого из 7
оставшихся агентов — не повторять грабли.

(1) СПЕЦИАЛИСТ = EXECUTION-ONLY. Нельзя оборачивать интерактивный промпт агента в
    stateless-специалиста: он задаст вопрос и ПОТЕРЯЕТ состояние (ответ юзера уйдёт
    оркестратору, не специалисту). Перед переносом ВЫРЕЖЬ из промпта все шаги
    «спроси / уточни / жди ответа / подтверди». Весь человек-в-цикле держит
    оркестратор; специалисту — только готовое ТЗ.
    (Пример: write_task_draft НЕ переиспользует agent-tasks — у него отдельный
    execution-only промпт. generate_cjm переиспользует agent-cjm лишь потому, что
    его интерактивный Режим 0 не триггерится на конкретном ТЗ.)

(2) НЕ ПОКАЗЫВАЙ ВНУТРЕННЮЮ КУХНЮ. В промпте оркестратора и специалиста запрети:
    «делегирую специалисту», «поручаю агенту», «вызываю…», «беру контекст»,
    «я специалист». Инструменты вызываются молча. Специалист пишет сразу для
    конечного пользователя, без мета-нарратива о себе/процессе. Нельзя, чтобы одно
    и то же (напр. разбор метрики) проговаривалось ДВАЖДЫ — оркестратором и потом
    специалистом. После возврата специалиста оркестратор НЕ пересказывает результат
    (специалист уже показал карточку), завершает только блоком suggestions.

(3) АГЕНТНОСТЬ vs ВОПРОСЫ (порядок «сначала выясни, потом уточняй»):
    - КОНТЕКСТ, который добывается инструментами (метрики, воронка, артефакты,
      существующие задачи, МАСШТАБ проблемы — проценты/жалобы/отклонение от плана),
      ассистент ОБЯЗАН находить САМ. Спрашивать это у пользователя ЗАПРЕЩЕНО.
    - Продуктовые РЕШЕНИЯ, которых нет в данных (приоритет и т.п.), — коротко
      уточнить (это контроль пользователя).
    - СТРОГИЙ ПОРЯДОК: сначала молча собрать контекст инструментом, ПОТОМ задать
      ровно нужный вопрос. Не наоборот, не вперемешку.
    - Бюджет вопросов: 1-2 максимум, только то, что реально нужно; пропусти, если
      юзер уже указал или просит «просто сделай».
    - НЕ спрашивай про поля, которых нет в модели данных (у черновика нет
      исполнителя/срока — их не спрашивать).
    - ФОРМУЛИРОВКИ БЕЗ ДВУСМЫСЛЕННОСТИ: слово «объём» модель прочитала как «данные о
      масштабе проблемы» и полезла спрашивать данные. Проверяй промпт на такие
      слова-ловушки.

(4) ЧИПЫ suggestions ПО ТЕКУЩЕМУ ХОДУ (не противоречить своему же сообщению):
    - Задал вопрос с вариантами -> чипы = САМИ варианты ответа (клик = ответ).
    - Завершил задуманное -> чипы = следующие действия (подтолкнуть дальше).
    - Никогда посторонние / противоречащие текущему сообщению.
    Правило уже в base — при переводе агентов держать его консистентным.

(5) НАДЁЖНОСТЬ: промпт-контроль на Haiku/Qwen — вероятностный, НЕ гарантия. Строгие
    однозначные формулировки снижают осечки, но не убирают. Где поведение должно
    быть ЖЕЛЕЗНЫМ (выбор приоритета, выбор метрик QBR, выбор сценария CJM) — выноси
    контроль в ДЕТЕРМИНИРОВАННЫЙ UI-элемент (как metric-selector, рендерится кодом),
    а не полагайся на «модель вспомнит». Честный измеритель регрессий — тест-сет
    интента/поведения на Vitest (нужен при любой архитектуре).

(6) ЭКСКЛЮЗИВНОЕ ВЛАДЕНИЕ WRITE-ИНСТРУМЕНТОМ. Если у агента есть правило рендера
    карточки-результата (task-link / cjm-result / artifact-result / html-report),
    отдай его write-инструмент ТОЛЬКО специалисту (убери из оркестратора) — тогда
    правило карточки живёт у специалиста, а не в лёгком base, и создание гарантированно
    идёт через специалиста. Исключение — интерактивные stateful-правки (напр.
    update_cjm для правки/отвязки артефакта): их оставляем инлайн у оркестратора.

(7) UI-КОНВЕНЦИИ (держать едиными для всех карточек/чипов):
    - Навигационные карточки-результаты: справа только стрелка «→», без слова «Открыть».
    - Чипы suggestions — карточки (grid, стрелка ↪ внизу), не «пилюли».
